Fusing an IMU and Wheel Encoders A practical, math-grounded guide to multi-rate sensor fusion with a Kalman filter, and how to drop it into ROS 2 / Nav2 on EyeRobot.

EyeRobot already produces wheel odometry: state_estimator_node.py integrates the firmware's encoder tick counts into a nav_msgs/Odometry message on /odom. This guide shows how to add an IMU and let a Kalman filter blend the two — even though they arrive at different rates — into one smooth, drift-reduced pose, and how that plugs into Nav2.

TL;DR Run an Extended Kalman Filter (robot_localization/ekf_node). Feed it the encoder body velocities (vx, ωz) from /odom and the IMU yaw rate + orientation. The filter's predict step runs at a fixed high rate; each sensor triggers an update whenever its message lands, so mismatched frequencies are handled natively — no resampling needed. Let the EKF own the odom→base_link TF and set publish_tf:=false in our estimator.

1 · Why fuse at all

No single sensor gives you a good pose. They fail in complementary ways, which is exactly what makes fusing them worthwhile:

SourceGood atBad at
Wheel encodersLinear velocity vx, short-term distance. Quiet, high-resolution.Heading drift that accumulates forever (wheel slip, unequal radii, the 0.150 m track-width error all integrate into yaw).
IMU gyro (ωz)Fast, clean angular rate; catches slip the wheels can't see.Bias drift → integrating raw gyro into an absolute angle also drifts (slower than wheels, but still).
IMU accelDetects real motion / bumps.Double-integrating to position is hopeless on a ground robot — noise & gravity leakage dominate. Rarely fused for x/y.

The encoder yaw and the gyro yaw drift independently. A filter that weighs each by its trustworthiness produces a heading better than either alone — and a velocity estimate that survives a wheel slipping. That weighing, done optimally and recursively, is the Kalman filter.

2 · The Kalman filter, concretely

The filter tracks a belief about the state: a mean vector x and a covariance matrix P (how uncertain we are, and how the uncertainties correlate). For a planar robot a typical state is:

x = x
y
θ
vx
ωz   position (m), heading (rad), body-frame forward speed (m/s), yaw rate (rad/s)

It runs a two-phase loop. Predict rolls the state forward with a motion model. Update pulls the state toward whatever a sensor just measured, by an amount set by the relative uncertainties.

Predict (time update)

x̂k− = f(x̂k−1, uk)   push the mean through the motion model
Pk− = F Pk−1 Fᵀ + Q     grow the uncertainty (F = ∂f/∂x; Q = process noise)

Uncertainty always grows during predict — that's the model admitting it isn't perfect. Q encodes "how much do I trust my motion model per second."

Update (measurement update)

When a sensor delivers a measurement z, with a function h(x) that says what that sensor should read given the state:

yk = zk − h(x̂k−)      innovation: measured − expected
Sk = H Pk− Hᵀ + R    innovation covariance (R = sensor noise)
Kk = Pk− Hᵀ Sk−1     Kalman gain
x̂k = x̂k− + Kk yk    correct the mean
Pk = (I − Kk H) Pk−   shrink the uncertainty

The gain K is the whole story. Read it as a ratio:

Intuition for the gain K ≈ P / (P + R). If the filter is uncertain (large P) and the sensor is precise (small R), K→1 and we jump to the measurement. If the sensor is noisy (large R), K→0 and we mostly keep our prediction. The filter automatically trusts each sensor in proportion to how good it is — that is why a precise gyro can correct a drifting encoder heading without you hand-tuning a blend.

3 · Why different frequencies "just work"

This is the part that confuses people, so here it is plainly: predict and update are separate steps that do not have to run at the same rate, and updates from different sensors are independent of one another.

  • The predict step advances the state by Δt using the motion model. Δt can be anything — the model is continuous, so you predict forward to the exact timestamp of whatever happens next.
  • Each update is triggered by a message arriving. The IMU at 100 Hz fires its update 100×/s; the encoders at, say, 20–30 Hz fire theirs whenever a new tick count lands. Each uses its own h, H and R.
  • Because every measurement carries a timestamp, the filter predicts to that stamp, applies that one sensor's update, and moves on. A slow sensor simply contributes fewer corrections; it is never "waiting" for the fast one.
The real requirement It isn't matched rates — it's trustworthy timestamps and a common clock. Every header.stamp must be the true sampling time, and all nodes must share one time source (real time, or use_sim_time everywhere). Out-of-order or mis-stamped messages are what actually break multi-rate fusion, not the frequency gap.

4 · Plain KF, EKF, or UKF?

The vanilla Kalman filter is provably optimal — but only when the motion and measurement models are linear (f and h are matrices) and the noise is Gaussian. Check our motion model:

xk+1 = xk + vx cos(θ) Δt
yk+1 = yk + vx sin(θ) Δt
θk+1 = θk + ωz Δt

Those sin θ / cos θ terms are nonlinear in the state. A plain KF cannot represent them. So for any ground robot that estimates heading, the plain KF is off the table.

FilterHandles nonlinearity by…Use it when
KFnothing — models must be linear matricesState is linear (e.g. fusing two pure velocity sources with no heading in the state). Rare for mobile bases.
EKF ✅linearizing f,h each step via their Jacobians (F = ∂f/∂x, H = ∂h/∂x)Default for wheeled robots. Cheap, well-understood, and what robot_localization ships. Accurate when the per-step motion is small (true at 30–100 Hz).
UKFpropagating sample ("sigma") points through the true nonlinear f,hStrong nonlinearity / large steps where the EKF's linear approximation degrades. ~2–3× the cost. Also in robot_localization (ukf_node).
Recommendation for EyeRobot Use the EKF (ekf_node). The differential-drive model is mildly nonlinear and the loop runs fast, so the linearization error per step is tiny — the EKF is accurate, cheap, and the documented Nav2 path. Reach for the UKF only if you later see heading estimates degrade during hard, fast turns.

5 · What to actually feed the filter

A golden rule with robot_localization: fuse velocities, not absolute pose, from dead-reckoning sources. Encoder x/y/θ is just an integral of the wheel velocities — it always drifts, and feeding an ever-drifting absolute position to the filter poisons it. Feed the rates instead and let the filter do the integration once, consistently.

From the encoders (/odom) Fuse vx (twist.linear.x) and ωz (twist.angular.z). Ignore the absolute x/y/θ in the pose part for fusion.
From the IMU Fuse ωz (angular_velocity.z) always. Optionally fuse absolute yaw (from orientation) if the IMU has a magnetometer/decent fusion; otherwise leave orientation out and rely on the gyro rate.

Both sources supply ωz — that's deliberate. The filter blends the two yaw-rate estimates by their covariances, and the cleaner gyro pulls heading away from encoder slip. vx comes only from the wheels (the IMU can't observe forward speed well on the flat).

REP-103/105: all of this lives in base_link (x forward, y left, z up; yaw CCW-positive). Make sure the IMU is mounted/configured to that convention or correct it in the driver.

6 · The robot_localization config

The fusion is configured, not coded. Each sensor gets a 15-element boolean vector telling the EKF which of its fields to ingest, in this fixed order:

[ x, y, z,   roll, pitch, yaw,   vx, vy, vz,   vroll, vpitch, vyaw,   ax, ay, az ]

An ekf.yaml for EyeRobot (one encoder odom + one IMU, planar):

### config/ekf.yaml — EyeRobot encoder + IMU fusion ###
ekf_filter_node:
  ros__parameters:
    frequency: 30.0            # filter output / predict rate (Hz)
    two_d_mode: true           # planar robot: zero out z, roll, pitch
    publish_tf: true           # EKF owns odom -> base_link
    publish_acceleration: false

    map_frame: map
    odom_frame: odom
    base_link_frame: base_link
    world_frame: odom        # fusing continuous data -> world = odom

    # ---- Source 0: wheel-encoder odometry (fuse BODY VELOCITIES only) ----
    odom0: /odom
    odom0_config: [false, false, false,
                  false, false, false,
                  true,  false, false,   # vx
                  false, false, true,    # vyaw
                  false, false, false]
    odom0_differential: false
    odom0_queue_size: 10

    # ---- Source 1: IMU (fuse yaw + yaw rate) ----
    imu0: /imu/data
    imu0_config: [false, false, false,
                 false, false, true,    # yaw (drop if no magnetometer)
                 false, false, false,
                 false, false, true,    # vyaw (gyro) — always fuse this
                 false, false, false]
    imu0_differential: false
    imu0_remove_gravitational_acceleration: true
    imu0_queue_size: 20
Two nodes must not fight over a TF Exactly one node may broadcast odom→base_link. Once the EKF does it (publish_tf: true above), our wheel estimator must stop: launch state_estimator with publish_tf:=false (the node already exposes that parameter for precisely this hand-off — see its docstring). It keeps publishing /odom as a fusion input; the EKF publishes the transform.

Picking the covariances (this is the tuning)

The filter only weighs sensors correctly if their reported covariances are honest. They live on the messages, not in the EKF:

  • Encoder twist covariance — already set in state_estimator_node.py (twist_x_cov, twist_yaw_cov). Make twist_yaw_cov deliberately larger than the IMU's gyro variance so the filter prefers the gyro for heading rate.
  • IMU covariance — set angular_velocity_covariance and orientation_covariance in the IMU driver from the datasheet / a stationary Allan-variance measurement.
  • Rule of thumb: relative magnitudes matter more than absolute. If heading lags slip, lower the IMU yaw-rate variance (or raise the encoder's).

7 · Wiring it into EyeRobot

  1. Get an IMU publishing sensor_msgs/Imu on /imu/data, stamped in base_link (or a fixed imu_link with a static transform). Options:
    • micro-ROS Add an IMU publisher to the ESP32 firmware. Note the entity budget (see DOCS.md): we publish 10 topics today and RMW_UXRCE_MAX_PUBLISHERS=12, so one IMU publisher fits — but it's the 11th, so mind the headroom and the shared-UART bandwidth at 100 Hz.
    • host Or hang the IMU off the host (USB/I²C) with a dedicated ROS 2 driver node. Keeps it off the micro-ROS link entirely and is usually simpler to time-stamp well.
  2. Confirm the encoder /odom twist is populated — it is: the estimator fills twist.linear.x and twist.angular.z with windowed averages and sets their covariances. That's already an EKF-ready input.
  3. Add ekf.yaml (above) under ManualController/config/ and install the directory in CMakeLists.txt / setup.py.
  4. Hand off the TF: launch state_estimator with publish_tf:=false; launch the EKF with publish_tf:=true.
  5. Add the EKF node to the launch file:
from launch_ros.actions import Node

ekf = Node(
    package='robot_localization',
    executable='ekf_node',
    name='ekf_filter_node',
    output='screen',
    parameters=[os.path.join(pkg_share, 'config', 'ekf.yaml')],
)
# and pass right_/left_… as before; just add `ekf` to the LaunchDescription list,
# and set the state_estimator node's publish_tf parameter to False.

Install once: sudo apt install ros-$ROS_DISTRO-robot-localization, and add <exec_depend>robot_localization</exec_depend> to package.xml.

8 · How this slots into Nav2

Nav2 doesn't fuse sensors itself — it consumes the result. Two things it needs, both delivered by the EKF:

Nav2 needsProvided byUsed for
A continuous, smooth odom→base_link TFEKF publish_tfLocal costmap rolling window; the controller server (DWB/MPPI/RPP) tracking the robot frame-to-frame. Must be smooth & continuous — no jumps — which is exactly what fusing the IMU buys you.
An odometry topic (nav_msgs/Odometry)EKF /odometry/filteredThe controller's velocity feedback / collision-checking. Point the controller and costmaps at /odometry/filtered rather than the raw /odom.

The global side is separate: SLAM (slam_toolbox) or AMCL provides map→odom, correcting the slow odom drift against a map. So the full chain Nav2 sees is:

map (AMCL/SLAM, discrete jumps) → odom (EKF: encoder+IMU, smooth) → base_link → sensors
Why the two-layer split matters to Nav2 Nav2's controllers assume odom→base_link never jumps (they differentiate it for velocity). Global fixes (loop closures, AMCL corrections) are discrete jumps, so they go on map→odom instead. The EKF fusing IMU+encoders is what keeps the odom layer jump-free — that is its job in the stack.

A second EKF instance (fusing GPS, world_frame: map) is how robot_localization handles the global layer outdoors — see Docs/docs.nav2.org/tutorials/docs/navigation2_with_gps.rst. Indoors, AMCL/SLAM fills that role.

Verify, in order:

ros2 topic echo /imu/data --qos-reliability best_effort   # IMU alive, sane covariance
ros2 topic echo /odom                                      # twist.linear.x / angular.z populated
ros2 node info /ekf_filter_node                            # subscribed to /odom AND /imu/data
ros2 topic hz /odometry/filtered                           # ~30 Hz steady
ros2 run tf2_ros tf2_echo odom base_link                   # smooth, no jumps
One-paragraph summary A Kalman filter keeps a mean + covariance, predicts with the motion model at a fixed rate, and updates per measurement — so a fast IMU and slow encoders fuse natively via timestamps, no resampling. The robot's heading makes the model nonlinear, so use the EKF. Feed it encoder vx+vyaw and IMU vyaw(+yaw); the gyro corrects encoder slip via the Kalman gain. In ROS 2 this is robot_localization/ekf_node + an ekf.yaml; it owns odom→base_link and emits /odometry/filtered, which is exactly the smooth, continuous odom layer Nav2 needs underneath a global map→odom from AMCL/SLAM.
